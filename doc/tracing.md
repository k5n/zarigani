# tracing の利用について

このプロジェクトでは `tracing` を「実行時の観測（診断・障害調査）用」のログ出力に採用している。  

## なぜ `tracing` を採用したか

1. `actix` の非同期・メッセージ駆動の流れを追いやすい
   - 1 件のメッセージがどの actor を経由し、どこで失敗したかを可視化しやすい。
   - `info_span` + `Instrument` で処理単位の文脈を持たせられる。

2. 構造化ログが書ける
   - 文字列を整形して読み取るより、`actor=...`, `conversation_id=...` などのキー付きフィールドとして記録できるため、後からの絞り込み・検索が容易。

3. 運用時のログ切り替えが容易
   - `tracing-subscriber` の `EnvFilter` で環境変数 `RUST_LOG` を使い、実行時にログレベルを調整できる。
   - 将来、JSON/ファイル出力や外部計装 (OpenTelemetry 等) への拡張がしやすい。

4. 「ユーザー向け表示」と「内部観測」の役割分担
   - CLI の `user> ` や `zarigani> ` は UI。  
     これらは `println!` のまま保持し、内部の状態追跡は `tracing` へ集約する方針にしている。

## 使い分けルール

### ログ対象 (`tracing`) にするもの

- actor 起動・停止・初期化
- メッセージ受信・送信開始・完了
- Provider/Dispatcher への送受信結果
- actor 間通信エラー
- リトライ・再試行・例外的な分岐

### ログ対象にしないもの (`println!` のまま)

- CLI プロンプト表示（`user> `）
- 返信表示（`zarigani> ...`）
- 見た目調整用空行や単なる操作案内

### ログの粒度とレベル（運用ルール）

- `info!`
  - actor 起動、主要ハンドリング成功、主要経路の完了
- `debug!`
  - メッセージ内容詳細、履歴長、内部ディスパッチの追加情報
- `warn!`
  - 期待内だが通常外を取る状態（未登録ルートなど）
- `error!`
  - `mailbox` 通信失敗、provider 応答不能、ルーティング失敗など復旧が必要な異常

## 現在採用している共通フィールド

可読性と追跡しやすさのため、主要なイベントに共通フィールドを付与する。

- `actor`
- `conversation_id`
- `message_id`
- `channel_kind`
- `participant_id`
- `history_len`（Provider 側）
- `provider`, `error`（文脈に応じて）

補足として、メッセージ本文そのものは現在は最小限にし、機密性とノイズを抑える方針。必要な場合だけ `debug!` で扱う。

## このドキュメントで理解しておくべきこと

このプロジェクトの tracing は「監視システム」ではなく「開発・運用デバッグ基盤」を目的としている。  
まずは `actix` の actor メッセージの流れを分解し、どこで何が起きたかを再現しやすくすることが第一目的。  
将来、ログの保存先をファイル/JSON/OpenTelemetry に変更する場合も、`tracing` のイベント設計がそのまま再利用できる前提で運用を続ける。
